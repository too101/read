# READ — Linux port (X11/Xlib)

พอร์ต [`read.asm`](../dos) (โปรแกรมอ่านข้อความภาษาไทยสำหรับ DOS) มาเป็น
โปรแกรม Linux เขียนด้วยภาษา C เรียก X11 (Xlib) ตรง ๆ — โครงสร้างเดียวกับ
พอร์ต[วินโดวส์](../windows) (asm ล้วน เรียก Win32 GDI ตรง ๆ): ตรรกะแกนกลาง
ทั้งหมด (byte classification, การแปลรหัส KU/TIS, การประกอบสระ/วรรณยุกต์
แบบ combining mark, สไตล์ WordStar, การสร้างตารางบรรทัด, ขีดจำกัดการเลื่อน
จอ) เขียนแยกอิสระจากพอร์ตวินโดวส์แต่ตรงกันทุกจุดเพราะแปลจากตรรกะเดียวกัน —
เปลี่ยนแค่ชั้น windowing/framebuffer จาก Win32 GDI เป็น X11 เท่านั้น

## สถานะ

**Build ผ่านสะอาด และยืนยันด้วยภาพหน้าจอจริงแล้ว** (รันใน X server แบบ
headless ด้วย Xvfb + `xdotool` + ImageMagick `import`): เปิดไฟล์ได้ วาดตัว
อักษรไทย การประกอบสระ/วรรณยุกต์ กรอบตาราง และสไตล์ WordStar ทุกแบบถูกต้อง
**ลากขยาย/ย่อหน้าต่างแล้วเนื้อหาปรับตามจริง** (ทดสอบลาก 640×475 → 960×570
เนื้อหาขยายเต็มพื้นที่ใหม่ถูกต้อง, ลากลงต่ำกว่าขั้นต่ำก็ไม่ crash แค่โดนตัดภาพ
ตามพื้นที่จริง) ไม่มี error จาก X11 ตลอดการทดสอบ

## Build

ต้องมี GCC, libX11 และ libXext (สำหรับส่วนขยาย MIT-SHM) dev headers:

```
sudo apt install build-essential libx11-dev libxext-dev   # Debian/Ubuntu
sudo dnf install gcc libX11-devel libXext-devel           # Fedora
sudo pacman -S base-devel libx11 libxext                  # Arch
```

แล้วรัน:

```
./build.sh
```

หรือสั่งตรง ๆ:

```
mkdir -p output
gcc -O2 -o output/read src/read_linux.c -lX11 -lXext
```

(ถ้า X server ปลายทางไม่มีส่วนขยาย MIT-SHM โปรแกรมจะ fallback ไปใช้วิธีส่ง
ภาพแบบเดิมอัตโนมัติ ไม่ crash — ดูหัวข้อ "ประสิทธิภาพ" ด้านล่าง)

ผลลัพธ์จาก build อยู่ที่ `output/read` (ไม่ commit เข้า git — สร้างใหม่ได้
เสมอด้วย `./build.sh`)

## วิธีใช้ / ปุ่มควบคุม

เหมือนพอร์ตวินโดวส์และเวอร์ชัน DOS ทุกประการ:

```
./output/read [ไฟล์]
```

ไม่ใส่ชื่อไฟล์ = แสดงหน้า help ในตัว · ลูกศรขึ้น/ลง เลื่อนทีละบรรทัด ·
PgUp/PgDn/Space/Backspace เลื่อนทีละหน้า · Home/End ไปต้น/ท้ายไฟล์ ·
ลูกศรซ้าย/ขวา เลื่อนแนวนอน 8 คอลัมน์ · `C` สลับรหัส KU/TIS ·
`F1` เปิด/ปิดหน้า help · `Q`/Esc ออกจากโปรแกรม (คลิกปุ่มปิดหน้าต่างก็ได้)

## หน้าต่างปรับขนาดได้ (resizable)

เริ่มต้นที่ 640×475 พิกเซล (80×24) เหมือนเดิม แต่ลากขยาย/ย่อได้แล้ว —
จำนวนคอลัมน์/บรรทัดคำนวณใหม่จากขนาดหน้าต่างจริงทุกครั้งที่ลาก (ฟอนต์บิตแมป
8×19 คงเดิมเสมอ ลากใหญ่ขึ้น = เห็นเนื้อหาเยอะขึ้น ไม่ใช่ตัวอักษรใหญ่ขึ้น)
ดัก X11 event `ConfigureNotify`: คำนวณคอลัมน์/บรรทัดใหม่ (ขั้นต่ำ 20×3),
สร้าง framebuffer/`XImage` ใหม่ตามขนาด, คงตำแหน่งเลื่อนจอเดิมไว้ (ไม่รีเซ็ต
กลับบนสุด) แล้ววาดใหม่ — ตั้ง `XSizeHints`'s `PMinSize` ไว้ด้วยเพื่อกัน
window manager ลากหน้าต่างเล็กกว่าที่ใช้งานได้จริง

ตอนลากขยาย/ย่อ (หรือกดปุ่มเลื่อนจอค้างเร็ว ๆ) X11 จะส่ง event มาเป็นชุดรัว ๆ
(`ConfigureNotify` หลายอันระหว่างลาก, `KeyPress` หลายอันจาก key-repeat) —
โค้ดจะ "รวบ" event ที่ค้างอยู่ในคิวก่อนวาดจริง (เอาแค่ขนาด/ตำแหน่งล่าสุด
ไปวาดครั้งเดียว แทนที่จะ recreate framebuffer + วาดทั้งจอ + `XPutImage`
ทุก event ที่เข้ามา) เพื่อไม่ให้หน่วงเวลาใช้งานผ่าน display ที่ forward
ระยะไกล เช่น WSLg บน WSL (ซึ่งมี overhead ต่อการส่งภาพแต่ละครั้งสูงกว่า
X11 บนเครื่องเดียวกันตรง ๆ) — ผลลัพธ์สุดท้ายเหมือนเดิมทุกกรณี แค่ข้าม
เฟรมกลาง ๆ ที่ไม่มีใครเห็นทัน

**การเลื่อนจอทีละบรรทัด** (ลูกศรขึ้น/ลง ซึ่งเป็นการกระทำที่เกิดถี่ที่สุดตอน
อ่านไฟล์) มี fast path แยกต่างหาก: แทนที่จะ redraw ทั้งหน้าต่างแล้วส่งภาพ
ทั้งก้อนใหม่ทุกครั้ง (ซึ่งขนาดข้อมูลคงที่เท่าพื้นที่หน้าต่างไม่ว่าจะเปลี่ยน
จริงแค่ไหน) โค้ดจะเลื่อนพิกเซลที่แสดงอยู่แล้วบนจอด้วย `XCopyArea` (คำสั่งที่
ทำงานฝั่ง X server เอง แทบไม่มีข้อมูลต้องส่งผ่านสายเลย) แล้ววาด+ส่งเฉพาะ
สองส่วนที่เปลี่ยนจริง ๆ คือแถบสถานะ (เลข R: เปลี่ยนทุกครั้ง) กับบรรทัดใหม่
หนึ่งบรรทัดที่เลื่อนเข้ามา — ใช้เฉพาะกรณีเลื่อนทีละ 1 บรรทัดพอดีและไม่มี
อะไรอื่นเปลี่ยน (ไม่ใช่ PgUp/PgDn/Home/End ที่กระโดดหลายบรรทัด ไม่ใช่ตอน
สลับโหมด KU/TIS หรือ help ซึ่งเปลี่ยนทุกตัวอักษร) กรณีอื่นนอกจากนี้ยังคง
redraw ทั้งจอตามปกติ ซึ่งถูกต้องอยู่แล้วและไม่บ่อยเท่า

**กรณีที่ยังต้อง redraw ทั้งจอ** (PgUp/PgDn ที่กระโดดข้ามไปทั้งหน้าไม่มี
บรรทัดไหนซ้ำกับหน้าเดิมเลย, resize, เปิดโปรแกรม) ใช้ส่วนขยาย **MIT-SHM**
ของ X11 ถ้า X server รองรับ (ปกติรองรับแทบทุกที่ รวมถึง WSLg): แทนที่จะให้
ไคลเอนต์ copy ข้อมูลภาพทั้งก้อนใส่ X protocol request ทุกครั้ง จะสร้าง
framebuffer เป็น shared-memory segment ที่ X server อ่านพิกเซลออกไปได้
โดยตรง ตัดการ copy ข้อมูลซ้ำซ้อนฝั่งไคลเอนต์ออกไป — ถ้า X server ไม่รองรับ
ส่วนขยายนี้ (ตรวจตอนเปิดโปรแกรมครั้งเดียว) จะ fallback ไปใช้การส่งภาพแบบ
`XPutImage` ปกติอัตโนมัติ ไม่มีผลต่อพฤติกรรมหรือความถูกต้องของภาพที่แสดง
เลย (ยืนยันด้วย pixel-diff เทียบทั้งสองโหมดแล้วว่าเหมือนกัน 100% รวมถึง
ตรวจสอบว่า shared-memory segment ถูกเก็บกวาดไม่รั่วไหลทั้งตอน resize และ
ตอนปิดโปรแกรมด้วย `ipcs -m`)

**ถ้ากด Maximize แล้วจอดำ (พอเลื่อนเมาส์ถึงขึ้นเนื้อหา)**: อาการนี้ยังพบอยู่
แม้หลังเพิ่มตัวดัก `VisibilityNotify` (ด้านล่าง) แล้ว — ค้นเพิ่มเติมพบว่าตรง
กับบั๊กที่มีรายงานอยู่แล้วใน WSLg เอง ไม่ใช่จุดที่เกิดจากโค้ดพอร์ตนี้: ตัวอย่าง
[microsoft/wslg#372](https://github.com/microsoft/wslg/issues/372) ("Resizing
window leads to not updating display any further") และ
[microsoft/wslg#1058](https://github.com/microsoft/wslg/issues/1058)
("maximized windows disappear") ทั้งคู่รายงานอาการเดียวกัน คือจอค้าง/ว่างหลัง
resize หรือ maximize จนกว่าจะมี event อื่นมากระตุ้น ซึ่งชี้ไปที่ชั้น compositor
ของ WSLg เอง (Weston ใน pipeline Xwayland → Weston → RDP ไปยัง Windows host)
ไม่ใช่ตัวโปรแกรม — โปรแกรมส่งพิกเซลที่ถูกต้องออกไปแล้วจริง ๆ ตั้งแต่ตอน
resize (โค้ดเดียวกับตอน resize ปกติที่ใช้งานได้) เพียงแต่ฝั่ง compositor ทำ
ภาพนั้นหายไประหว่างการเปลี่ยนสถานะ maximize เอง การขยับเมาส์ไม่ใช่ event ที่
โปรแกรมนี้ตอบสนองอยู่แล้ว ("ขยับเมาส์แล้วขึ้น" จึงไม่ใช่โปรแกรมไปดัก event
ที่เคยพลาด แต่เป็นตัว compositor ฝั่ง Windows ถูกกระตุ้นให้ repaint เองจาก
สาเหตุอื่นที่ไม่เกี่ยวกับ X11 เลย) — แก้จากฝั่งโปรแกรมโดยตรงไม่ได้ แต่เพิ่ม
มาตรการเสริมอีกชั้น: หลัง resize ทุกครั้งจะตั้งตัวจับเวลา (`repaint_pending`
+ `select()` timeout บน connection ของ X, ไม่ใช่ X11 event) ให้ส่งภาพเดิมซ้ำ
อีกครั้งหลังผ่านไป 200ms โดยไม่ต้องรอ event ใด ๆ เข้ามาก่อน — เผื่อว่าภาพที่
ส่งไปตอน resize/maximize ครั้งแรกเป็นครั้งที่ compositor ทำหาย ก็ยังมีอีก
ครั้งตามมาให้จับได้โดยไม่ต้องรอผู้ใช้ขยับเมาส์เอง (ราคาถูก แค่ส่งภาพซ้ำเฉย ๆ
ถ้าครั้งแรกไม่ได้หาย) — จุดนี้ก็ยังทดสอบใน sandbox ที่ไม่มี compositor จริง
แบบ WSLg ไม่ได้เหมือนกัน (ทดสอบได้แค่ว่าโค้ดใหม่ไม่ค้าง/ไม่ crash และไม่
กระทบพฤติกรรมปกติ) ถ้ายังเจออาการนี้อยู่หลังอัปเดต รบกวนแจ้งอีกทีว่าดีขึ้น
บ้างไหม (เช่น ใช้เวลานานขึ้นกว่าจะจอว่างอีกครั้ง หรือหายไปเลย)

**ตอนเปิดโปรแกรม** เนื้อหาแรกจะถูกส่งไปวาดทันทีหลังสร้างหน้าต่างเสร็จ
ไม่รอ X11 event `Expose` (ซึ่งบางสภาพแวดล้อมที่มี compositor เช่น WSLg
อาจส่งช้าหรือส่งเป็นส่วน ๆ ระหว่างเล่น animation เปิดหน้าต่าง ทำให้เห็น
หน้าต่างว่าง ๆ ก่อนสักพักค่อยขึ้นเนื้อหา หรือขึ้นมาไม่เต็มแล้วค่อยเต็มทีหลัง)

**ขีดจำกัดการเลื่อนแนวนอน (`C:` ในแถบสถานะ)** คำนวณจากความกว้างบรรทัด
ที่ยาวสุดลบคอลัมน์ที่แสดงได้ (`maxh = max(maxlen - cols, 0)`) แบบเดียวกับ
DOS ทุกประการ **รวมถึงการนับความกว้างของไฟล์รหัส KU: `build_lines` แปลง
รหัส KU→TIS ก่อนจัดประเภทไบต์เสมอ (`classify(translate(raw))`) ไม่ใช่นับ
จากไบต์ดิบ** ทำให้ไบต์สระ/วรรณยุกต์แบบ KU นับเป็น 0 คอลัมน์ตรงตามที่จะ
ปรากฏบนจอจริง (ซ้อนบนตัวฐาน ไม่ใช่กินพื้นที่ 1 คอลัมน์เต็ม) เดิมทีเคย
พบว่า `read.asm` ต้นฉบับนับจากไบต์ดิบ (ไม่แปลงรหัสก่อนนับ) ทำให้ DOS ยอม
เลื่อนแนวนอนได้ไกลเกินจริง — เมื่อตรวจสอบแล้วพบว่านั่นเป็นบั๊กของ `read.asm`
เอง ไม่ใช่พฤติกรรมที่ตั้งใจ จึงแก้ `read.asm` ให้แปลงรหัสก่อนนับด้วย (ผ่าน
ตาราง `trc` ตัวเดียวกับที่ใช้วาดข้อความจริง) แทนที่จะทำให้พอร์ตนี้ "เลียนแบบ
บั๊ก" — ตอนนี้ DOS/Windows/Linux นับความกว้างบรรทัดตรงกันทั้งสามแพลตฟอร์ม
และตรงกับสิ่งที่ปรากฏบนจอจริง (ทดสอบไฟล์รหัส KU เดียวกัน ได้ค่าเลื่อน
สูงสุดตรงกันทั้งสามฝั่ง) ไฟล์ที่ไม่ใช่รหัส KU ไม่กระทบเลย (`translate()`
เป็น no-op เมื่อไม่ได้เปิดโหมด KU)

## สิ่งที่ทำต่างจากเวอร์ชัน DOS โดยตั้งใจ

เหมือนพอร์ตวินโดวส์ทุกข้อ (ดู README ของ [`windows/`](../windows) สำหรับ
รายละเอียด): ไม่มีโหมด CGA/EGA/VGA/Hercules ให้เลือก, โหลดทั้งไฟล์ลง memory
ก้อนเดียว ไม่อ่านเป็นบล็อก 64KB, ไม่มี selftest (`/t`) และยังไม่รองรับ
ลาก-วางไฟล์

## ต่างจากพอร์ตวินโดวส์ตรงไหน

- เขียนด้วย C ธรรมดา ไม่ใช่ assembly ล้วนแบบพอร์ตวินโดวส์ — ใช้ X11 (Xlib)
  แทน Win32 GDI: framebuffer เป็น array ธรรมดา (`malloc`) blit ผ่าน
  `XImage`/`XPutImage` แทน DIB section/`BitBlt`
- ใช้ C มาตรฐาน/POSIX ตรง ๆ (`argv`, `malloc`, `fopen`) ไม่มีข้อจำกัดแบบ
  "no CRT" ที่ตั้งใจไว้เฉพาะพอร์ต asm บนวินโดวส์ เพราะ libX11 เองก็ผูกกับ
  libc อยู่แล้ว การเขียนเป็น asm ล้วนจะไม่ได้ประโยชน์ด้านขนาด/dependency
  เพิ่มขึ้นจริง (ดูรายละเอียดเหตุผลใน README ของ [`windows/`](../windows))
- หน้าต่างปิดโดยกดปุ่มปิด (X) ได้ถูกต้อง (ดัก `WM_DELETE_WINDOW`)
- หน้า help (`HELP_LINUX.TXT`) ปรับข้อความให้ตรงกับพอร์ตนี้ (คำสั่งเรียกใช้
  เป็น `read ไฟล์` แทน `read.exe ไฟล์`, เครดิตบอกว่าเป็น "Linux Port (X11)")
  ส่วนตารางคีย์/ตัวอย่างสไตล์/เครดิตฟอนต์เหมือนกับพอร์ตวินโดวส์ทุกไบต์

## สมมติฐานเรื่องจอภาพ

โค้ดสมมติว่า X display เป็น TrueColor ความลึกสี 24 หรือ 32 บิต (เกือบทุก
เครื่อง Linux ปัจจุบันเป็นแบบนี้) เพราะสีทั้งหมดที่ใช้เป็นโทนเทา (R=G=B)
เรื่อง byte order ของแต่ละความลึกสีจึงไม่กระทบสีที่เห็น

```
                     gen_data.py ใหม่ -- ดูคำเตือนเรื่องรูปแบบไบต์ด้านล่าง)
gen_data.py          สคริปต์สร้าง src/data.h ใหม่จาก ../dos/AXV.FON,
                     ../dos/KU.INC, ../dos/STATUS.INC และ HELP_LINUX.TXT
build_help_linux.py  สคริปต์ dev-time ที่ใช้แก้ ../windows/HELP_WIN.TXT
render_help.py       เป็น HELP_LINUX.TXT พร้อมเรนเดอร์เป็นภาพตรวจสอบก่อน
                     build จริง -- ไม่จำเป็นต้องรันเองปกติ, แต่ render_help.py
                     มีประโยชน์เดี่ยว ๆ ด้วยสำหรับตรวจสอบ HELP_LINUX.TXT
                     ก่อน build จริงหลังแก้ไข: `python3 render_help.py`
build.sh             สคริปต์ build บน Linux
```

⚠️ **`HELP_LINUX.TXT` ไม่ใช่ text ธรรมดา** — มีไบต์ TIS-620 ภาษาไทยปนกับไบต์

ตัวอักษรฐาน/tab เป็น 1 คอลัมน์ สไตล์/สระ-วรรณยุกต์/ไบต์กลืนนับเป็น 0) ไม่งั้น
