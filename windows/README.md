# READ.exe — Windows port (Pure x86 Assembly, ไม่มี C/CRT เลย)

พอร์ต [`read.asm`](../dos) (โปรแกรมอ่านข้อความภาษาไทยสำหรับ DOS) มาเป็น
โปรแกรมวินโดวส์ เขียนด้วย **x86 assembly (NASM) ล้วน ๆ** เรียก Win32 API
ตรง ๆ ผ่าน kernel32.dll/user32.dll/gdi32.dll เท่านั้น — ไม่มี C runtime,
ไม่มี libc, ไม่มี `main()`/`WinMain()` แบบภาษา C คั่นกลางเลยสักบรรทัด
(entry point คือ `_start` ที่เขียนเองทั้งหมด รวมถึง heap allocation,
การแปลง command line, การแปลงตัวเลขเป็นข้อความสำหรับแถบ status ฯลฯ)

ตรรกะการทำงาน (การอ่านไฟล์, การจัดบรรทัด, การประกอบสระ/วรรณยุกต์ภาษาไทย,
สไตล์ WordStar แบบตัวหนา/เอียง/ขีดเส้นใต้ ฯลฯ, ปุ่มควบคุม) ตรงกับ
[พอร์ต Linux](../linux) ทุกประการเพราะแปลจากตรรกะแกนกลางเดียวกัน — ต่างกัน
แค่ชั้นเรียก windowing API (Win32 GDI ที่นี่ / X11 ที่ Linux)

## ทำไมเขียนเป็น asm ล้วน ไม่ใช้ C

Win32 API เรียกตรง ๆ ได้โดยไม่ต้องมี CRT/libc คั่นกลางเลย เพราะเป็น API
ระดับ OS ที่ไม่ผูกกับภาษา C runtime — ต่างจาก Linux ที่การวาดหน้าต่างต้อง
ผ่าน libX11 ซึ่งตัวมันเองก็เรียก libc อยู่แล้ว (ดูเหตุผลเต็มใน README ของ
[`linux/`](../linux)) พอร์ตนี้เลยตัด CRT ทิ้งได้จริงและได้ไฟล์เล็กมาก:
**~15.5 KB** stripped, import เฉพาะ 3 DLL (kernel32/user32/gdi32) รวม 33
ฟังก์ชัน ไม่มี CRT หลุดเข้ามาโดยไม่ได้ตั้งใจ

## บั๊กที่แก้ (หลังทดสอบบนเครื่องจริง)

- **ไม่ตัดข้อความท้ายไฟล์ที่ Ctrl-Z (1Ah)**: ไฟล์ข้อความ DOS เก่าจำนวนมาก
  (โดยเฉพาะที่มีโค้ดควบคุมเครื่องพิมพ์แบบ dot-matrix ต่อท้าย) ลงท้ายด้วยไบต์
  1Ah ซึ่งเป็นเครื่องหมาย EOF ตามธรรมเนียมของ DOS — เวอร์ชัน DOS เดิม
  (`read.asm`) หยุดสแกนไฟล์ทันทีที่เจอไบต์นี้ (ดู `bl_done` ใน `build_lines`)
  แต่พอร์ตนี้ (ก่อนแก้) กลับปฏิบัติกับ 1Ah เหมือน CR/LF ธรรมดา คือขึ้นบรรทัด
  ใหม่แล้วสแกนต่อ ทำให้โค้ดควบคุมเครื่องพิมพ์ที่อยู่หลัง Ctrl-Z แสดงเป็น
  ตัวอักษรเพี้ยน ๆ ท้ายไฟล์ — แก้โดยให้ `build_lines` หยุดสแกนทันทีที่เจอ 1Ah
  เหมือนเวอร์ชัน DOS ทุกประการ
- **สไตล์ "ตัวขยาย" (expand) เรนเดอร์เพี้ยนเป็นลายตาราง/แถบทึบ**: ผู้ใช้ทดสอบ
  บนวินโดวส์จริงแล้วพบว่าตัวอักษรที่ใช้สไตล์ขยาย (ตัวอย่างคำว่า "ตัวขยาย" ใน
  หน้า help) เรนเดอร์ออกมาเป็นลายทึบ/ลายตารางแทนที่จะเป็นตัวอักษรที่อ่านออก
  สาเหตุ: ฟังก์ชัน `blit_cell` วาดพิกเซลของสไตล์ขยายด้วยการเรียก `fb_pixel`
  **2 ครั้งต่อ 1 บิต** (เพราะขยายทุกพิกเซลเป็น 2 เท่า) โดยใช้ค่า on/off ที่เก็บ
  ไว้ใน register `eax` ซ้ำทั้งสองครั้ง — แต่ `fb_pixel` เองใช้ `eax` เก็บค่าสี
  ที่จะเขียนลงเฟรมบัฟเฟอร์ (caller-saved ตามข้อตกลงของโค้ดนี้) ทำให้หลังเรียก
  ครั้งแรก `eax` ถูกเขียนทับไปแล้ว พิกเซลที่สองของคู่ที่ขยายจึงได้ค่า on/off ที่
  ผิด (เกือบตลอดเวลาจะกลายเป็น "ติด" โดยไม่สนใจบิตจริงของฟอนต์) ผลคือได้ลาย
  ทึบ/ลายตารางแทนรูปตัวอักษรจริง — แก้โดย push ค่า `eax` ไว้ก่อนเรียกพิกเซล
  แรก แล้ว pop กลับมาใช้ก่อนเรียกพิกเซลที่สอง
- **ไฟล์รหัส KU เลื่อนแนวนอนได้ไกลเกินความจำเป็น (เคยแก้ผิดทาง แล้วแก้กลับ)**:
  ผู้ใช้ทดสอบไฟล์รหัส KU จริง พบว่า DOS เลื่อนได้ถึง `C:15` แต่พอร์ตนี้
  เลื่อนได้แค่ `C:1` — รอบแรกสรุปว่า `read.asm` ต้นฉบับถูกและพอร์ตนี้ผิด
  (เพราะ `build_lines` เรียก `translate()` ก่อนจัดประเภทไบต์ ขณะที่ `bl_c`
  ของ `read.asm` จัดประเภทไบต์ดิบตรง ๆ) จึงแก้พอร์ตนี้ให้จัดประเภทไบต์ดิบ
  เหมือนกัน ได้ `C:15` ตรงกับ DOS — แต่นั่นทำให้เลื่อนได้ "ไกลเกินจริง":
  ไบต์สระ/วรรณยุกต์แบบ KU ที่ยังไม่แปลงรหัสมักไม่ตกในช่วง combining mark
  ของ TIS-620 เลยถูกนับเป็น 1 คอลัมน์เต็มทั้งที่ตอนวาดจริงมันกว้าง 0
  (ซ้อนบนตัวฐาน) — ผลคือบรรทัดที่ "ดูแล้ว" กว้างแค่ 81 คอลัมน์บนจอ กลับ
  รายงานความกว้าง 95 แล้วยอมให้เลื่อนขวาเกินตัวอักษรจริงไปอีก 14 คอลัมน์
  เป็นจอว่าง ๆ ที่ไม่มีอะไรให้เลื่อนไปหาจริง ๆ (`bl_c` ของ `read.asm`
  ที่จัดประเภทไบต์ดิบไม่ใช่พฤติกรรมที่ถูกต้อง เป็นบั๊กของต้นฉบับ DOS เอง)
  แก้ที่ถูกต้องจริง ๆ คือย้อนพอร์ตนี้กลับไปแปลงรหัสก่อนจัดประเภท
  (`translate()` แล้วค่อย `classify()`) เหมือนเดิมตั้งแต่แรก แล้วแก้
  `read.asm` เองแทน ให้ `bl_c` ใช้ตาราง `trc` (ตารางเดียวกับที่ `RDCH`
  ใช้วาดข้อความจริง ซึ่งแปลง KU→TIS ไว้แล้วในตัว) แทนตาราง `cls` ดิบ ๆ —
  ตอนนี้ทั้ง DOS/Windows/Linux นับความกว้างบรรทัดแบบเดียวกัน คือนับตามที่
  จะปรากฏบนจอจริง ทดสอบกับไฟล์ที่ผู้ใช้ส่งมาแล้วทั้งสามแพลตฟอร์มได้
  `C:1` ตรงกันหมด (แก้ถูกแล้วบรรทัดที่กว้างสุด 81 คอลัมน์ ก็เลื่อนได้
  point เดียวพอดี ไม่มีจอว่างเกินจำเป็นอีกต่อไป) ไฟล์ธรรมดาที่ไม่ใช่รหัส KU
  ไม่กระทบเลยทั้งสองทิศทาง (`translate()` เป็น no-op เมื่อไม่ได้เปิดโหมด KU)
- **กด F1 เข้าหน้า help แล้วกด Esc ไม่กลับมาเอกสาร (ออกจากโปรแกรมไปเลย)**:
  `Esc`/`Q` เดิมเรียก `PostQuitMessage` ทันทีไม่ว่าจะอยู่ในโหมดไหน แต่
  `read.asm` (`v_ascii`) ถือว่า `Esc`/`Q` เป็นปุ่มธรรมดาเหมือนปุ่มอื่นตอนอยู่
  ในหน้า help — คือแค่ปิดหน้า help กลับไปที่เอกสาร ไม่ใช่ออกจากโปรแกรมเลย
  (จะออกจากโปรแกรมจริงก็ต่อเมื่อกดตอนไม่ได้อยู่ในหน้า help หรืออยู่ในหน้า
  help แบบ demo ที่ไม่มีไฟล์เปิดอยู่) แก้ให้ `Esc`/`Q` เช็คโหมด help ก่อน
  เหมือนปุ่มอื่น ๆ แล้ว
- **ชื่อหน้าต่างเปลี่ยนจาก "READ.COM for Windows" เป็น "READ for Windows"**
  (โปรแกรมนี้ไม่ใช่ .COM แบบ DOS อีกต่อไป)

## หน้าต่างปรับขนาดได้ (resizable)

เริ่มต้นที่ 640×475 พิกเซล (80×25 — 1 แถว status + 24 แถวเนื้อหา เท่าโหมด
VGA text ของ DOS) เหมือนเดิม แต่ **ลากขยาย/ย่อหน้าต่างได้
แล้ว** (มีขอบหนา + ปุ่ม maximize ตามปกติ) โดยจำนวนคอลัมน์/บรรทัดที่แสดงจะ
คำนวณใหม่ตามขนาดหน้าต่างจริงทุกครั้งที่ลาก แทนที่จะสเกลตัวอักษร (ฟอนต์
บิตแมป 8×19 คงเดิมเสมอ ลากใหญ่ขึ้น = เห็นตัวอักษรเยอะขึ้น ไม่ใช่ตัวอักษร
ใหญ่ขึ้น):

- ดัก `WM_SIZE`: อ่านความกว้าง/สูงใหม่จาก `lParam`, คำนวณจำนวนคอลัมน์ =
  กว้าง/8 และจำนวนบรรทัด = สูง/19 - 1 (เผื่อแถบ status), ถ้าต่ำกว่าขั้นต่ำ
  (20 คอลัมน์ × 3 บรรทัด) จะปัดขึ้นเป็นขั้นต่ำแทน แล้วสร้าง DIB section/
  memory DC ใหม่ตามขนาดจริง (ลบตัวเก่าด้วย `DeleteObject`/`DeleteDC` ก่อน
  กันหลุด GDI handle) จากนั้นคำนวณขอบเขตเลื่อนจอใหม่ (`recompute_bounds`
  — **ไม่ใช่** `calc_limits` ตัวเดิม เพื่อไม่ให้ตำแหน่งเลื่อนจอ/แนวนอนรีเซ็ต
  กลับไปบนสุดทุกครั้งที่ลากขอบหน้าต่างนิดเดียว) แล้ววาดใหม่ทั้งจอ
- ดัก `WM_GETMINMAXINFO`: กำหนด `ptMinTrackSize` (ขนาดต่ำสุดที่ Windows
  เองจะยอมให้ลาก) ไว้ล่วงหน้า กันไม่ให้ผู้ใช้ลากหน้าต่างเล็กจนโปรแกรม
  ใช้งานไม่ได้ (เผื่อกรอบ/แถบชื่อหน้าต่างแบบคร่าว ๆ ไม่ได้คำนวณละเอียดผ่าน
  `AdjustWindowRect` — ใช้เป็นแค่ "พื้น" ขั้นต่ำ ในทางปฏิบัติ Windows เองก็
  บวกขนาดกรอบ/แถบชื่อเพิ่มให้อยู่แล้วจึงไม่มีทางเล็กกว่านี้จริง)

พอร์ต [Linux](../linux) มีฟีเจอร์เดียวกัน (ดัก `ConfigureNotify` แทน
`WM_SIZE`) — ทดสอบแบบ dynamic จริงสำเร็จแล้วที่นั่น (ลากขยาย/ย่อ ยืนยันด้วย
ภาพหน้าจอจริง) ส่วนพอร์ตนี้ยังไม่มี Wine ในสภาพแวดล้อมที่ทดสอบให้ยืนยันแบบ
เดียวกันได้ (ดูหัวข้อสถานะการทดสอบด้านล่าง) แต่ตรรกะการคำนวณคอลัมน์/บรรทัด
จากขนาดพิกเซลเป็นสูตรเดียวกันทั้งสองพอร์ต

## สถานะการทดสอบ

**ทดสอบด้วย Wine ในสภาพแวดล้อม headless ได้บางส่วนระหว่างพัฒนา** (ก่อน
เพิ่มฟีเจอร์ resizable) ยืนยันได้ว่า:

- คอมไพล์และลิงก์ผ่านสะอาด ไม่มี error/warning จาก NASM หรือ linker
- ไฟล์ .exe ที่ได้เป็น PE32 GUI executable ที่ถูกต้อง (ตรวจด้วย `objdump`)
  import เฉพาะ 3 DLL ตามที่ตั้งใจ ไม่มี CRT หลุดเข้ามาโดยไม่ได้ตั้งใจ
- รันบน Wine แล้วหน้าต่างเปิดขึ้นมาได้ วาดฟอนต์ภาษาไทยถูกต้อง รวมถึงการ
  ประกอบสระ/วรรณยุกต์แบบ combining mark, สไตล์ WordStar ทุกแบบ, เส้นกรอบ
  (box-drawing), และแถบ status ที่สร้างข้อความเองด้วยมือ (ไม่ใช้ snprintf)
- โหลดไฟล์และจัดบรรทัด (`build_lines`) ทำงานถูกต้องกับไฟล์ทดสอบภาษาไทย
- ทดสอบปุ่มกดพื้นฐานสำเร็จ (ลูกศรขวา เลื่อนแนวนอน เห็น C: ในแถบ status
  เปลี่ยนค่าและเนื้อหาเลื่อนตามจริง)

**การเพิ่มฟีเจอร์ resizable และการอัปเดตหน้า help ล่าสุด ยังไม่ได้ทดสอบ
แบบ dynamic** — รอบล่าสุดนี้ไม่มี Wine ติดตั้งอยู่ในสภาพแวดล้อมที่ใช้พัฒนา
เลย (ต่างจากพอร์ต Linux ที่มี X11 headless ให้ทดสอบได้จริง) ยืนยันได้แค่
ระดับ static: compile/link สะอาดไม่มี error/warning, import table มี
ฟังก์ชันที่ใช้ครบ (`DeleteObject`, `DeleteDC`, `GetDC`, `ReleaseDC`,
`InvalidateRect`), ข้อมูล help ที่ฝังไว้ตรวจสอบด้วยการเรนเดอร์ผ่าน Python
(`render_help.py`, จำลอง `classify`/`apply_style`/`blit_cell` ชุดเดียวกับ
โปรแกรมจริง) แล้วตรงตามที่ออกแบบไว้ — แต่**ยังไม่เคยเห็นหน้าต่างจริงถูกลาก
ขยายบนวินโดวส์จริงสักครั้งเดียว** ควรลองรันบนเครื่องจริงก่อนเชื่อถือเต็มที่
โดยเฉพาะเรื่องขนาดตัวอักษร/ระยะขอบตอนลากบ่อย ๆ ติด ๆ กัน และตอน maximize
หน้าต่าง ถ้าเจอตรงไหนแปลก ๆ (เช่น เนื้อหาไม่รีเฟรช, ขอบเพี้ยน, ลากเล็กสุด
แล้วค้าง) แจ้งได้เลย จะแก้ให้

## Build

ต้องมี 2 โปรแกรมบน PATH (รายละเอียดใน `build.bat`):

1. **NASM** — https://www.nasm.us/
2. **MinGW-w64 รุ่น 32-bit (i686)** — https://winlibs.com/ (เลือกรุ่น
   Win32/i686 ไม่ใช่ x86_64) ใช้แค่ `ld.exe` (linker) กับไฟล์ import library
   ของ kernel32/user32/gdi32 ที่แถมมาด้วยเท่านั้น **ไม่ได้เรียก gcc หรือ CRT
   ใด ๆ** — เลือกใช้ MinGW-w64 เพราะหาไฟล์ import library สำเร็จรูปง่ายสุด

แล้วรัน:

```
build.bat
```

หรือสั่งเองทีละขั้น:

```
mkdir output
nasm -f win32 -Isrc\ src\read_win.asm -o output\read_win.o
ld -e _start --subsystem windows -o output\read.exe output\read_win.o -lkernel32 -luser32 -lgdi32
strip output\read.exe
```

(`-Isrc\` จำเป็น — `data.inc` อยู่ใต้ `src/` และ NASM ไม่ค้นหาโฟลเดอร์ของ
ไฟล์ต้นทางเองโดยอัตโนมัติเวลาสั่งจากโฟลเดอร์แม่แบบนี้)

ผลลัพธ์จาก build อยู่ที่ `output\read.exe` (x86 32-bit, ~15.5 KB, ไม่ commit
เข้า git — สร้างใหม่ได้เสมอด้วย `build.bat`)

## วิธีใช้ / ปุ่มควบคุม

เหมือนพอร์ต Linux และเวอร์ชัน DOS ทุกประการ:

```
output\read.exe [ไฟล์]
```

ไม่ใส่ชื่อไฟล์ = แสดงหน้า help ในตัว · ลูกศรขึ้น/ลง เลื่อนทีละบรรทัด ·

ลูกศรซ้าย/ขวา เลื่อนแนวนอน 8 คอลัมน์ · `C` สลับรหัส KU/TIS ·
`F1` เปิด/ปิดหน้า help · `Q`/Esc ออกจากโปรแกรม

## โครงสร้างไฟล์

```
output/read.exe   ผลลัพธ์จาก build (~15.5 KB, x86 32-bit, ไม่มี CRT --
                  ไม่ commit เข้า git — สร้างใหม่ได้เสมอด้วย build.bat)
src/read_win.asm  ซอร์สโค้ดทั้งหมด (~1840 บรรทัด NASM)
src/data.inc      ฟอนต์ AXV 8x19 + ตาราง KU→TIS + ข้อความ help ที่ฝังไว้
                  (สร้างจาก gen_data.py -- ไม่ควรแก้ไฟล์นี้ตรง ๆ)
HELP_WIN.TXT      ข้อความหน้า help ที่ใช้จริง (แก้ตรงนี้ได้ แล้วรัน
                  gen_data.py ใหม่ -- ดูคำเตือนเรื่องรูปแบบไบต์ด้านล่าง)
gen_data.py       สคริปต์สร้าง src/data.inc ใหม่จาก ../dos/AXV.FON,
                  ../dos/KU.INC, ../dos/STATUS.INC และ HELP_WIN.TXT
build_help_win.py สคริปต์ dev-time ที่ใช้แก้ ../dos/HELP.TXT เป็น
render_help.py    HELP_WIN.TXT พร้อมเรนเดอร์เป็นภาพตรวจสอบก่อน build จริง
                  -- ไม่จำเป็นต้องรันเองปกติ, แต่ render_help.py มีประโยชน์
                  เดี่ยว ๆ ด้วยสำหรับตรวจสอบ HELP_WIN.TXT หลังแก้ไข:
                  `python3 render_help.py`
build.bat         สคริปต์ build บนวินโดวส์
```

⚠️ **`HELP_WIN.TXT` ไม่ใช่ text ธรรมดา** — มีไบต์ TIS-620 ภาษาไทยปนกับไบต์
ควบคุมสไตล์ WordStar และไบต์วาดกรอบตาราง แก้ไขด้วย text editor ทั่วไปได้
แต่ต้องระวังไม่ให้ความกว้างคอลัมน์ของแต่ละแถวในกรอบเปลี่ยน (นับเฉพาะ
ตัวอักษรฐาน/tab เป็น 1 คอลัมน์ สไตล์/สระ-วรรณยุกต์/ไบต์กลืนนับเป็น 0) ไม่งั้น
กรอบจะเบี้ยว — แก้แล้วรัน `python3 render_help.py` เพื่อดูภาพผลลัพธ์ก่อน
`gen_data.py` เสมอ
